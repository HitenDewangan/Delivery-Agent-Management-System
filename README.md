# Delivery Agent Management System

A full-stack admin application for managing delivery agents: create, view, edit, delete, search,
filter, paginate, and see dashboard statistics. Reads are cached in Redis (cache-aside); PostgreSQL
is always the source of truth.

## Technology stack

| Layer    | Technology                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------------- |
| Frontend | Next.js (App Router), TypeScript, Tailwind CSS 4, shadcn/ui-style components, TanStack Query, React Hook Form, Zod, Sonner |
| Backend  | Node.js, Express 5, TypeScript (strict), Zod                                                                               |
| Database | PostgreSQL 16, Prisma 7 (with the `pg` driver adapter)                                                                     |
| Cache    | Redis 7 via ioredis                                                                                                        |
| Testing  | Jest, ts-jest, Supertest                                                                                                   |
| Tooling  | ESLint, Prettier, Docker Compose, ts-node-dev                                                                              |

## Architecture

```
Browser ──HTTP──▶ Next.js (UI, port 3000) ──fetch──▶ Express API (port 4000)
                                                         │
                          routes → controllers → services → repositories → PostgreSQL (Prisma)
                                                    │
                                                    └──▶ Redis (cache-aside, optional at runtime)
```

- **Routes** map URLs to controllers. **Controllers** are thin: validate input with Zod, call a
  service, shape the response.
- **Services** hold business logic and orchestrate caching.
- **Repositories** are the only code that talks to Prisma, and translate database errors
  (unique violation → `409`, record not found → `404`).
- **Errors** are handled centrally (`error.middleware.ts`); internal details are never leaked.
- The frontend talks to the backend only through real HTTP calls (`frontend/src/lib/api.ts`).

```
backend/src/
├── config/        env validation (fails fast on bad config)
├── controllers/   HTTP layer
├── services/      agent.service.ts (business logic), cache.service.ts (Redis)
├── repositories/  agent.repository.ts (Prisma)
├── schemas/       Zod request schemas
├── routes/  middlewares/  lib/  utils/  types/
frontend/src/
├── app/           dashboard, agents list/new/[id]/[id]/edit
├── components/    ui primitives, layout shell, agent form/dialog/badge
├── hooks/         TanStack Query hooks, debounce
└── lib/  types/   API client, config, formatting
```

## Database design

One table, `agents` (`backend/prisma/schema.prisma`):

| Column      | Type                                                        | Notes                |
| ----------- | ----------------------------------------------------------- | -------------------- |
| id          | UUID, primary key                                           | generated by Prisma  |
| fullName    | text, required                                              |                      |
| phone       | text, required, **unique**                                  | stored normalized    |
| email       | text, required, **unique**                                  | stored lowercase     |
| serviceArea | text, required, indexed                                     |                      |
| status      | enum `ACTIVE` / `INACTIVE`, default `ACTIVE`, indexed       |                      |
| vehicleType | enum `BICYCLE` `MOTORCYCLE` `SCOOTER` `CAR` `VAN`, optional |                      |
| notes       | text, optional                                              |                      |
| createdAt   | timestamp, default now, indexed                             |                      |
| updatedAt   | timestamp                                                   | maintained by Prisma |

## Redis caching

Pattern: **cache-aside**. Reads check Redis first; on a miss the service reads PostgreSQL, stores
the result with a TTL, and returns it. Redis is never trusted over the database.

| Data            | Key                             | TTL (env)                        |
| --------------- | ------------------------------- | -------------------------------- |
| Agent list      | `agents:list:v<version>:<hash>` | `CACHE_TTL_LIST_SECONDS` (60)    |
| Dashboard stats | `agents:stats:v<version>`       | `CACHE_TTL_LIST_SECONDS` (60)    |
| Single agent    | `agents:detail:<id>`            | `CACHE_TTL_DETAIL_SECONDS` (120) |

- **Deterministic keys:** the hash is built from the sorted, normalized parameters (page, limit,
  status, service area, search; case-insensitive filters are lowercased), so equal queries share one
  entry.
- **Invalidation without `KEYS`/`SCAN`:** list and stats keys contain a version number stored at
  `agents:list:version`. After any successful create/update/delete the service increments it
  (`INCR`), so every list/filter/page variant becomes unreachable at once; the old entries expire
  via their TTL. Update and delete also remove `agents:detail:<id>`.
- **Order of operations:** the database write happens first; the cache is invalidated only after it
  succeeds. A failed update or delete leaves the cache untouched. The version is read before the
  database read, so data loaded around a concurrent write can never be filed under a fresh version.
- **Failure handling:** every Redis call is wrapped; on error the request is served from PostgreSQL
  and a warning is logged. `enableOfflineQueue: false` and a 1 s command timeout mean an outage
  costs about a millisecond, not a hang. The client reconnects automatically.
- **Known limitation:** if Redis is unreachable at the moment of a write, invalidation cannot
  happen, so cached reads can be stale for at most one TTL (60–120 s). "Not found" results are
  never cached.
- **Logs** (JSON): `cache hit`, `cache miss`, `cache set`, `cache invalidated`, and
  `cache error, falling back to database`.

## Environment variables

Never commit real `.env` files; only the `.env.example` templates are tracked.

| File                  | Variable                     | Default                 | Purpose                              |
| --------------------- | ---------------------------- | ----------------------- | ------------------------------------ |
| `.env` (root)         | `POSTGRES_USER`              | `delivery_user`         | Docker Postgres user                 |
|                       | `POSTGRES_PASSWORD`          | _required_              | Docker Postgres password             |
|                       | `POSTGRES_DB`                | `delivery_agents`       | Database name                        |
|                       | `POSTGRES_PORT`/`REDIS_PORT` | `5432` / `6379`         | Host ports                           |
| `backend/.env`        | `DATABASE_URL`               | _required_              | Must match the root `.env` values    |
|                       | `REDIS_URL`                  | _required_              | e.g. `redis://localhost:6379`        |
|                       | `PORT`                       | `4000`                  | API port                             |
|                       | `CORS_ORIGIN`                | `http://localhost:3000` | Allowed frontend origin              |
|                       | `CACHE_TTL_LIST_SECONDS`     | `60`                    | List/stats TTL                       |
|                       | `CACHE_TTL_DETAIL_SECONDS`   | `120`                   | Agent detail TTL                     |
| `frontend/.env.local` | `NEXT_PUBLIC_API_URL`        | `http://localhost:4000` | Backend base URL (no trailing slash) |

## Installation

Prerequisites: Node.js 20+, npm, Docker with Compose v2.

```bash
# 1. Environment files
cp .env.example .env
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env.local
# Set the same database password in .env and in DATABASE_URL inside backend/.env

# 2. PostgreSQL + Redis
docker compose up -d
docker compose ps                # both should become "healthy"

# 3. Install dependencies (backend postinstall runs `prisma generate`)
(cd backend && npm install)
(cd frontend && npm install)

# 4. Create the tables
(cd backend && npm run prisma:deploy)

# 5. Run (two terminals)
cd backend  && npm run dev       # http://localhost:4000
cd frontend && npm run dev       # http://localhost:3000
```

Open http://localhost:3000. Stop services with `docker compose down` (add `-v` to also delete data).

## Docker

`docker-compose.yml` runs PostgreSQL 16 and Redis 7 with health checks. PostgreSQL data is kept in
the `postgres_data` volume; Redis uses append-only persistence in `redis_data`. Credentials come
from the root `.env` (`POSTGRES_PASSWORD` is mandatory, compose refuses to start without it).

## API (`/api/v1`)

Success: `{ "success": true, "data": ..., "meta"?: ... }`.
Error: `{ "success": false, "error": { "code", "message", "details"? } }`.

| Method | Path                  | Description                                            | Success | Errors        |
| ------ | --------------------- | ------------------------------------------------------ | ------- | ------------- |
| POST   | `/agents`             | Create an agent                                        | 201     | 400, 409      |
| GET    | `/agents`             | List with search, filters, pagination                  | 200     | 400           |
| GET    | `/agents/stats`       | Totals, active/inactive, by vehicle, top service areas | 200     |               |
| GET    | `/agents/:id`         | Get one agent                                          | 200     | 400, 404      |
| PATCH  | `/agents/:id`         | Partial update (`null` clears `vehicleType` / `notes`) | 200     | 400, 404, 409 |
| DELETE | `/agents/:id`         | Delete an agent (`{ data: { id } }`)                   | 200     | 400, 404      |
| GET    | `/health` (no prefix) | Service, PostgreSQL and Redis status                   | 200/503 |               |

**List query params:** `page` (default 1), `limit` (default 10, max 100), `search` (name, email,
phone, service area), `status` (`ACTIVE`/`INACTIVE`), `serviceArea` (case-insensitive exact match).
The response includes `meta.pagination: { page, limit, total, totalPages }`.

**Validation:** names 2–100 chars; phone is normalized (spaces, dashes, brackets removed) and must
be 7–15 digits with optional leading `+`; email is trimmed and lowercased; unknown fields are
rejected; `:id` must be a UUID. Duplicate phone or email returns `409` with the offending fields.

`GET /health` returns `200` with `status: "ok"`, `200` with `"degraded"` if only Redis is down
(the API still works), or `503` with `"error"` if PostgreSQL is down.

```bash
curl -X POST localhost:4000/api/v1/agents -H 'Content-Type: application/json' \
  -d '{"fullName":"Asha Rao","phone":"+91 98765 43210","email":"asha@example.com","serviceArea":"Indiranagar","vehicleType":"MOTORCYCLE"}'
curl 'localhost:4000/api/v1/agents?search=asha&status=ACTIVE&page=1&limit=10'
curl localhost:4000/api/v1/agents/stats
```

## Testing

```bash
cd backend
npm test                                                   # unit + route tests, no services needed
REDIS_INTEGRATION_URL=redis://localhost:6379 npm test      # also runs tests against a real Redis
npm run test:coverage
npm run typecheck                                          # type checks src and tests
```

- **Schemas:** validation, normalization, pagination defaults and limits.
- **Routes (Supertest):** the real Express app, validation, services and error handling, with only
  the repository (the Prisma boundary) replaced by a mock.
- **Cache:** hit/miss behaviour, TTLs, per-filter keys, version invalidation after create, update
  and delete, no invalidation when the database write fails, graceful fallback and recovery when
  Redis is down, and a real-Redis integration suite.
- **Migrations:** apply `prisma/migrations/*/migration.sql` to an empty database
  (`prisma migrate deploy`) and confirm with `prisma migrate status`.

## Troubleshooting

- **`Cannot find module '../generated/prisma/client'`** – run `npm run prisma:generate` in `backend/`.
- **`password authentication failed`** – the password in `backend/.env` differs from the one the
  Postgres volume was created with. Fix it, or recreate the volume with `docker compose down -v`.
- **Frontend shows "Cannot reach the server"** – start the backend and check `NEXT_PUBLIC_API_URL`
  and `CORS_ORIGIN`.
- **Redis stopped** – the app keeps working from PostgreSQL; `/health` reports `degraded`.
